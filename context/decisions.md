### 2026-10-24 — Target framework changed to .NET 10 LTS
**Decision**: TargetFramework is `net10.0-windows`; the SDK is installed with winget (Microsoft.DotNet.SDK.10).
**Reason**: .NET 8, the original spec, reaches end of support on 2026-11-10; .NET 10 LTS is supported until 2028-11.
**Alternatives**: Stay on .NET 8 (no security updates after 17 days).
**Consequences**: The tech stack in CLAUDE.md was updated; `global.json` pins 10.0.x.
**Author**: User decided

### 2026-10-24 — Widgets mount on SHELLDLL_DefView, above the icons
**Decision**: The surface is a child window of `SHELLDLL_DefView`, z-ordered above `SysListView32`.
**Reason**: Widgets must be clickable and draggable; putting them behind the icons (the WorkerW approach of wallpaper engines) would have the icon list view intercept all mouse input. Mount on DefView rather than its parent: DefView exists in both the new and the old hierarchy, and when Explorer moves it to a WorkerW in the old one the widgets travel with it.
**Alternatives**: Mount on WorkerW (behind the icons, no input); mount on the Progman/WorkerW container (left behind when DefView is moved away in the old version); a top-level HWND_BOTTOM window (covered by Win+D, needs extra detection).
**Consequences**: Widgets cover the icons under them; widgets stay visible when "Show desktop icons" is off.
**Author**: Claude (deduced from the spec "mount on the desktop icon layer")

### 2026-10-24 — The surface is a layered child window (UsesPerPixelTransparency)
**Decision**: `HwndSource` + `WS_CHILD` + `UsesPerPixelTransparency` (→ `WS_EX_LAYERED`).
**Reason**: On 24H2+ Progman carries `WS_EX_NOREDIRECTIONBITMAP`, and a non-layered child window is not drawn; it also gives per-pixel transparency and click-through on transparent pixels.
**Alternatives**: A WPF `Window` + `SetParent` (a Window is a poor child window, and positioning a layered one is error-prone).
**Consequences**: WPF renders in software + UpdateLayeredWindow; performance is acceptable for small widgets.
**Author**: Claude

### 2026-10-24 — Re-mounting = rebuilding the HwndSource
**Decision**: Every (re-)mount creates a new `HwndSource` and reuses the same WPF content object.
**Reason**: Measured: when explorer exits, cross-process child windows are destroyed; a single code path is simplest, and the content state is kept.
**Alternatives**: `SetParent` on a still-living HWND (one more path, which was measured not to happen).
**Consequences**: Detection is `HwndSource.Disposed` (→ `DesktopSurface.Lost`) plus `TaskbarCreated`, retrying on a 1-second `DispatcherTimer` until it succeeds.
**Author**: Claude

### 2026-10-24 — Stage 2 config semantics
**Decision**: Widget positions are stored in physical screen pixels (clamped back if they fall outside the work area on load); the panel column count is a single global setting; a rescan purges settings of folders/items that no longer exist (changing the root folder is equivalent to a fresh start); if the root folder is unusable at startup → a message, then the default is used and written back to config.
**Reason**: Physical pixels agree with `DesktopSurface`, so positions don't move when the scaling changes; a global column count is like a phone folder and needs no per-widget UI; config reflects only the existing folders.
**Alternatives**: DIPs / work-area-relative fractions; per-widget column counts; keeping stale settings forever; quitting after the message.
**Consequences**: A folder restored from the Recycle Bin after deletion returns to the default position.
**Author**: User decided

### 2026-10-24 — Scanning and config coordination split into FolderScanner + WidgetCatalog
**Decision**: `FolderScanner` handles only the file system (scanning, watcher, debounce, rename events); `WidgetCatalog` merges scan results with config (ordering, purging, rename transfer, saving).
**Reason**: Single responsibility; the merge logic (`Reconcile`) is a pure function that can be tested without touching the disk.
**Alternatives**: FolderScanner depending on ConfigStore and doing everything.
**Consequences**: Later UI only subscribes to `WidgetCatalog.Changed`.
**Author**: Claude

### 2026-10-24 — Events serialized by SynchronizationContext, full rescan after debounce
**Decision**: `FolderScanner` captures the `SynchronizationContext` it was created on (throwing if there is none) and posts all events back in order; after the debounce the whole root folder is rescanned, with no incremental updates.
**Reason**: Config is accessed only on the UI thread, so no locks are needed; a rename always precedes the refresh that follows. The data is small (dozens of folders × dozens of items), so a rescan costs next to nothing and cannot miss an event.
**Alternatives**: A background thread + lock; incremental updates per event.
**Consequences**: Tests must create the scanner on a WPF Dispatcher thread (the `DispatcherThread` helper).
**Author**: Claude

### 2026-10-24 — Item scope and default order
**Decision**: Items = the visible files in a widget folder (skipping hidden/system files, subfolders, loose files in the root folder); the first order is Explorer's natural sort, later new items are appended at the end.
**Reason**: The spec supports .lnk/.url/.exe/ordinary files and not folders; desktop.ini and Office temp files shouldn't show up; appending matches the intuition of adding an app on a phone.
**Alternatives**: Re-sort by name or modified time every time; show subfolders as items.
**Consequences**: There is no manual reorder UI for now; order is determined by the order of adding.
**Author**: Claude (conventional default, reported to the user at the stage)

### 2026-10-24 — Items always show icons, never content thumbnails
**Decision**: `SIIGBF_ICONONLY`; images, PDFs and videos also show their file-type icon.
**Reason**: Per the spec, "get the icon"; everything is square and consistent like a phone folder; no thumbnail generation is triggered, so it's faster.

### 2026-10-24 — Shell icons are read as straight alpha
**Decision**: Copy the pixels from the DIB section and build with `PixelFormats.Bgra32`.
**Reason**: Measured: several icons have pixels with RGB > A, which can't occur in a premultiplied format, so it is straight alpha; `CreateBitmapSourceFromHBitmap` drops alpha.
**Alternatives**: `Pbgra32` (edges come out too bright, and pixels with alpha=0 but a color become visible noise).
**Consequences**: If some Shell handler returns premultiplied data, edges would be slightly dark (not observed).
**Author**: Claude

### 2026-10-24 — IconService threading and cache
**Decision**: Shell calls and composition run on a single dedicated STA thread; the cache is memory only, keyed by (path, LastWriteTimeUtc) and caching the `Task`; the preview key from the first 4 items decides whether to rebuild; `Retain` purges on every catalog refresh.
**Reason**: Shell handlers can be slow and must not block the UI; frozen bitmaps can cross threads; the mtime makes "rebuild only when the file changes" need no extra events.
**Alternatives**: Fetching images synchronously on the UI thread; a disk cache; multi-threaded fetching.
**Consequences**: At startup each item is fetched from the Shell once; when a shortcut target's icon changes but the .lnk doesn't, it isn't updated.
**Author**: Claude

### 2026-10-24 — Widget look, size, default position, grid alignment
**Decision**: A light translucent rounded square; 48 DIP (same size as a native medium icon); new widgets are laid out from the top right of the primary monitor's work area downward; snapped to the grid on release.
**Reason**: The user chose after seeing comparison images (A/B/C × 48/64/80).
**Alternatives**: Dark translucent / no base; 64, 80 DIP; top left / screen center; free placement.
**Consequences**: The small icons inside are about 18 DIP; native icons on the right will overlap.
**Author**: User decided

### 2026-10-24 — Cell definition and conflict handling
**Decision**: A cell = the widget's 76×96 DIP slot (converted to physical pixels by the monitor DPI), anchored at the top right of the work area; one widget per cell; loading and releasing both snap to "the nearest free cell".
**Reason**: 76×96 is close to the native icon cell spacing; one rule handles dragging, loading and old coordinates after a DPI change, so positions are always on the grid and never overlap.
**Alternatives**: Allow overlap; swap positions when dropped on an occupied cell; anchor at the top left.
**Consequences**: Dropping on an occupied cell lands in the next nearest free cell; the cells don't align with Windows' native icon cells (different origin).
**Author**: Claude (implementation detail after the user chose "align to the grid", reported to the user)

### 2026-10-25 — Window approach for the Acrylic panel
**Decision**: The Acrylic style uses `SingleBorderWindow` + `WindowChrome(GlassFrameThickness=-1, CaptionHeight=0)`, removes `WS_SYSMENU`, and measures the content itself to set Width/Height (no SizeToContent); other styles use a layered window.
**Reason**: Measured: a borderless `WS_POPUP` gets no system backdrop; with `WS_SYSMENU` DWM draws a close button in the extended frame; SizeToContent counts the frame that was removed, making the window too big and running off the screen.
**Alternatives**: Faking the blur ourselves (a layered window can't sample what is behind it); offering only plain colors.
**Consequences**: Acrylic vs layered must be decided before the window is created, so every panel opening builds a new window (which also picks up the latest settings).
**Author**: Claude

### 2026-10-25 — The desktop surface doesn't activate the desktop (MA_NOACTIVATE)
**Decision**: `DesktopSurface` answers `WM_MOUSEACTIVATE` with `MA_NOACTIVATE`.
**Reason**: Measured: clicking a widget while a panel is open activated the Explorer desktop, and Explorer swallowed that click, so the widget never saw the press (clicking another widget took two clicks). With the desktop not activated, opening and closing the panel is decided entirely by `PanelController`, and the "don't reopen for 500 ms after closing" guard is no longer needed.
**Alternatives**: Keep the desktop activation + a timing guard + recapturing the mouse (tried; the press never arrived, so it didn't work).
**Consequences**: Clicking a widget doesn't make the desktop the foreground window; dragging a widget while a panel is open doesn't close the panel.
**Author**: Claude

### 2026-10-25 — Items launched with Process.Start(UseShellExecute)
**Decision**: Launch with `Process.Start` + `UseShellExecute=true` (internally ShellExecuteEx); working directory = the item's folder; `ErrorDialog=true`.
**Reason**: Meets "always ShellExecute", simpler than hand-writing SHELLEXECUTEINFO; behaves like a double-click in File Explorer; errors are shown by Windows itself.
**Alternatives**: Calling `ShellExecuteEx` directly through CsWin32.
**Consequences**: Failures (including a cancelled UAC) are only logged.
**Author**: Claude

### 2026-10-25 — Drop rules and the start-with-Windows mechanism
**Decision**: Ordinary files → create a shortcut; `.lnk`/`.url` not from the desktop → always copy; folders → create a shortcut; `.exe` → create a shortcut (spec); desktop shortcuts → per the drop mode (spec). Start with Windows uses the HKCU Run key.
**Reason**: Chosen by the user; creating shortcuts never moves the user's documents by accident and leaves the Start menu etc. in place. The Run key needs no administrator and shows in Task Manager's "Startup apps".
**Alternatives**: Ordinary files per the drop mode or always copy; other shortcuts treated like desktop ones; Task Scheduler; the Startup folder.
**Consequences**: A Run value that exists while Task Manager has disabled it counts as off; when we toggle, we clear that flag.
**Author**: User decided

### 2026-10-25 — XAML does not reference types of this assembly
**Decision**: Dialog texts are set in code-behind, not with `x:Static res:Strings.*`; `Strings` stays internal.
**Reason**: Referencing a local type from XAML triggers WPF's temporary markup assembly compilation, and `Strings` is generated by resx into `obj/` at build time, which the temporary assembly can't compile against.
**Alternatives**: Putting the generated Strings.Designer.cs into the source (needs manual syncing); a custom build target that generates it earlier (would add the Compile item twice).
**Consequences**: Every window has a `LocalizeTexts()` section.
**Author**: Claude

### 2026-10-25 — Widget grid uses the desktop's native icon cells; taskbar pinning uses a self-made shortcut
**Decision**: (1) A widget's cell size and anchor come from Explorer's icon list view (reading `LVM_GETITEMPOSITION` across processes), avoiding cells occupied by native icons. (2) "Pin to taskbar" doesn't call an undocumented pin API; it builds `%APPDATA%\DeskGrid\Pins\<name>.lnk` (`DeskGrid.exe --open "name"`, the icon being the preview) and selects it in File Explorer for the user to pin; at startup, if an instance is already running, it hands over through a named pipe and exits. (3) Dragging inside the panel: reorder in the same panel, dragging out is handled by the target; dragging onto another widget always moves.
**Reason**: The user reported that widgets weren't aligned with desktop icons and overlapped them; Windows 11 doesn't let programs pin on the user's behalf (undocumented APIs are fragile).
**Alternatives**: A fixed 76×96 cell (the old one, can't align); the undocumented `IPinnedList3` interface (may break with a Windows update); `WM_COPYDATA` instead of a named pipe.
**Consequences**: With multiple monitors the cell size follows what Explorer reports (unverified); when the native cells can't be read it falls back to the old grid. An icon the user drags onto a widget still overlaps.
**Author**: Claude (the user asked for the feature; the implementation awaits the user's verification)

### 2026-10-25 — Panel: drag animation (drag ghost + sliding), auto-open panel when dragging onto a widget, in-place title rename
**Decision**: (1) During a drag a `DragGhost` (a click-through topmost layered window) follows the cursor, the original cell is left empty and the other items slide aside with a `TranslateTransform` animation (iOS style); at the end the ghost flies back to the cell or shrinks away. When dragged off the panel the gap closes. (2) A drag (a panel item or an outside file) held over a widget for 550 ms → `PanelController.OpenForDrag` opens that folder's panel (not activated); the original panel is only hidden (DWM cloak) until the drag ends, because `DoDragDrop` runs inside it. An item from another folder dropped into the open panel → `ItemImporter.ImportTo` moves it in, then `WidgetCatalog.PlaceNewItem` puts it at the given position; before the drop the panel opens a gap at that cell. (3) Panel title: hover shows a pencil, a click turns it into a text box, Enter confirms, Esc cancels, losing focus confirms; renamed with `Directory.Move` (through a temporary name for case-only changes), with the settings carried over by the existing Renamed handling.
**Reason**: The user wanted an iOS-style drag experience and direct renaming.
**Alternatives**: Self-drawn mouse dragging instead of OLE (can't drag to the desktop / other programs); closing the original panel at once (would break the OLE drag loop).
**Consequences**: Panel dragging needs an RenderTransform on Items; when dropping into a panel whose rows are full, the new row doesn't enlarge the window height beforehand (a known limitation). Not verified on a real machine.
**Author**: Claude (the user asked for the feature)

### 2026-10-25 — Version check: GitHub releases decide, a three-choice dialog, self-update via a file-swap script
**Decision**: 8 seconds after startup and from the settings window button, look up `releases/latest`; when newer, a dialog: Update (download the single-file exe, verify `.sha256`, and a temporary PowerShell script overwrites the original exe after this process ends and restarts it), Keep (`skippedUpdateVersion` remembers that tag, automatic checks stop reminding), Cancel (stores nothing, reminds again at the next start). A development build (not single-file) or an install folder that isn't writable opens the release page instead of updating.
**Reason**: The user asked for version checking and automatic updating; a running exe can't overwrite itself, so an external script is needed.
**Alternatives**: A built-in updater exe (one more file to publish); no checksum verification (a tampered download would go unnoticed); `WM_COPYDATA` etc.
**Consequences**: Config gains `skippedUpdateVersion` (with the user's consent); an update of an unsigned exe has no SmartScreen protection, relying on SHA256 and GitHub HTTPS; the real file-swap flow can only be tested once a release newer than 0.1.0 exists.
**Author**: Claude (the user asked for the feature)

### 2026-10-25 — Disk / registry / network failures: log and keep running, don't crash the app
**Decision**: `ConfigStore.Save` on `IOException` / `UnauthorizedAccessException` (a sync client or antivirus locking the file, a full disk) only logs, and the next save rewrites everything; `AutoStart` returns `false` when registry access is denied; `UpdateChecker.ParseRelease` returns `null` for JSON with missing fields / wrong types; the update script is written with a UTF-8 BOM (Windows PowerShell 5.1 reads BOM-less files as ANSI, which garbles paths for non-ASCII user names); the log rotates to `.old` beyond 512 KB.
**Reason**: A global unhandled exception ends the program (fail-fast is kept), so foreseeable environment failures must be caught at the source, or one failed save would make all widgets on the desktop vanish.
**Alternatives**: Marking `DispatcherUnhandledException` as Handled (swallows real program errors too, and a timer exception would flood the log); `Save` returning success or not (callers can't do anything about it).
**Consequences**: When saving fails the user sees no message, only the log; settings may be lost partway through that run.
**Author**: Claude (the user asked to find and fix bugs)

### 2026-10-26 — Taskbar "all folders": one panel window switches between list and folder; pinned shortcuts each carry an AppUserModelID
**Decision**: The tray's "Pin all folders to the taskbar…" builds `%APPDATA%\DeskGrid\Pins\All\DeskGrid Folders.lnk` (`DeskGrid.exe --all`, exe icon), with the pipe message `*` (can't be a folder name). The panel opens in list mode at the cursor, the folder cells having the same base tile + 2×2 preview as desktop widgets; clicking a folder swaps in that folder's contents in the **same window** (launching, reordering, dragging out, renaming as before), with a ← at the left of the title back to the list. All pinned shortcuts get `System.AppUserModel.ID` (`DeskGrid.Pin.All`, `DeskGrid.Pin.Folder.<first 8 bytes of the name's SHA-256>`).
**Reason**: The user asked for a taskbar button that lists all folders and then behaves like the desktop folders. Switching in place avoids opening and closing two windows between dragging and activation; shortcuts of one exe without their own AppUserModelID get merged by the taskbar as the same app.
**Alternatives**: Opening a separate panel when a folder is clicked (two panels and focus to handle); a taskbar jump list (clicking the button doesn't show it directly).
**Consequences**: The folder cells in list mode don't accept drops and can't be dragged; folder-pin shortcuts built by older versions have no AppUserModelID and just need to be rebuilt.
**Author**: Claude (the user's requirement)

### 2026-10-26 — Drag-out detection uses physical pixels and is also checked in QueryContinueDrag; rescans during a drag are deferred
**Decision**: Whether the cursor left the panel is decided with `GetWindowRect` + `GetCursorPos` (physical pixels) and also checked on every `QueryContinueDrag`, not relying on `DragLeave` alone. A rescan that arrives during a drag is stored and applied after the release; for an item landing in the panel, even if it is rebuilt it stays hidden until the ghost arrives. `DragGhost` is positioned in `SourceInitialized` (before it is shown), with Lift / Land sharing one timer.
**Reason**: The user reported "dragging out sometimes doesn't close" and "the drag ghost sometimes displays wrongly". A DIP conversion counts a cursor that has just left through the right / bottom edge as inside, after which `DragLeave` never comes; rebuilding items mid-drag confuses the drag index and the original cell; showing the new cell at once after a reorder produced a double icon.
**Alternatives**: Not updating the panel at all during a drag (a deleted folder would show stale contents).
**Consequences**: The cause of item 2 is a guess, not reproduced.
**Author**: Claude

### 2026-10-26 — Icons of Store app shortcuts: the Apps folder + a fallback without icon-only
**Decision**: When a `.lnk` has no file path, take the parsing name of its ID list and ask for the icon of `shell:AppsFolder\<name>`; when `ICONONLY` yields a generic document icon, ask once more with `RESIZETOFIT`. Only if both fail use the ID list item itself, and last the `.lnk` file.
**Reason**: Asking for the icon of a Store app's `.lnk` gave a blank document. The WhatsApp package has no logo of the size `ICONONLY` asks for, so the Shell returns a generic icon; without `ICONONLY` it finds an 88 px logo. Measured: the same call fails in the test process once WPF is loaded, while the DPI-unaware thread context works in the test but not in DeskGrid (PerMonitorV2), so it isn't used.
**Alternatives**: Reading the package manifest to find the logo ourselves (needs WinRT PackageManager, costly); a DPI-unaware thread (doesn't work in this program).
**Consequences**: Such icons may be only 88 px; the preview shows them at 48 DIP, with little effect.
**Author**: Claude

### 2026-10-26 — The folder list's order is stored in config `folderOrder`
**Decision**: `AppConfig.FolderOrder` (a list of folder names) decides the order of the "all folders" panel; new folders go last, vanished ones are removed, a rename replaces in place. Dragging a folder carries only the custom format, not `FileDrop`.
**Reason**: Folder order can't be stored on disk, and for the same reason as item order (`ItemOrder`) it goes in config; no `FileDrop`, so the folder isn't moved when dropped on the desktop or another widget.
**Alternatives**: Sorting by name (can't be customized).
**Consequences**: `WidgetCatalog.Widgets` is sorted by it, which also affects the placement order of new widgets that have no stored position.
**Author**: User decided (asked for drag reordering), Claude implemented

### 2026-10-26 — Pressing the taskbar button again closes: remember the panel that a taskbar click closed
**Decision**: When a panel closes while the foreground window is the taskbar (`Shell_TrayWnd` / `Shell_SecondaryTrayWnd`), `PanelController` remembers that panel (`*` for the list, otherwise the folder name) and the time; a taskbar request for the same panel (`ToggleAtCursor` / `ToggleListAtCursor`) within 3 seconds counts as "close" and doesn't open it again.
**Reason**: Measured: pressing a taskbar button again while its panel is open did not close it: on the press the panel first loses focus and closes, and the second DeskGrid process started by the shortcut sends its request afterwards, when no panel is open, so it opens again.
**Alternatives**: Comparing only the time (after clicking another taskbar button, a DeskGrid button click within 3 seconds would be swallowed, a wider range); comparing the cursor position (users often move the mouse away right after clicking, unreliable).
**Consequences**: After closing the panel by clicking elsewhere on the taskbar first, clicking the same DeskGrid button within 3 seconds needs one extra click.
**Author**: Claude

### 2026-10-27 — The drag ghost becomes a pure Win32 layered window (its own window class)
**Decision**: `DragGhost` is no longer a WPF `Window` / `HwndSource`: it creates a `WS_EX_LAYERED` window with `RegisterClassEx` (`DefWindowProc`) + `CreateWindowEx`, draws the icon into a DIB section with `RenderTargetBitmap` and calls `UpdateLayeredWindow`; it redraws only when size / opacity change, and moving is just `SetWindowPos` (once per frame).

**Alternatives**: A built-in window class (such as Static) needs no registration, but the intent is unclear.
**Consequences**: `DragGhostTests` was added to check that drawing doesn't fail (it would fail if switched back to `HwndSource`).

### 2026-11-01 — Multiple monitors: widget positions follow the config; move the surface back when it drifts
**Decision**: (1) `DesktopSurface.Resync()` compares the window's actual screen position with `Position` and moves it back if they differ; `DesktopHost` checks every second and runs it at once on `WM_DISPLAYCHANGE`, raising `DisplayChanged` 1.5 seconds later, and `WidgetBoard.OnDisplayChanged` re-places by the positions stored in config. (2) A stored position that is on no monitor (one was unplugged) → temporarily placed on the nearest monitor, the stored value not overwritten, and it goes back automatically when the monitor returns. (3) The panel's `Reposition` always takes a DIP size and handles `WM_DPICHANGED`, so even with mixed DPI it hugs the widget.
**Reason**: The user reported that after connecting an external monitor and placing it left of the primary one, all widgets moved to the left and a panel opened on the left appeared on the primary one. Cause: the surfaces are children of Progman / DefView, which cover all monitors; when a monitor is added left of / above the primary one the parent's origin turns negative while the child windows' client coordinates stay the same → the whole batch drifts on screen; `Position` and the config didn't change, and the panel is positioned by `Position`, so it opened on the primary monitor. **Consequences**: When the primary monitor is replaced by another (the coordinate origin changes), the stored coordinates map to a different physical place; this case is not handled yet. An open panel is closed when the display settings change.
**Author**: The user asked for a thorough fix, the implementation was decided by me

### 2026-11-02 — Scanning robustness for a single shortcut / network target
**Decision**: (1) In `ShortcutFile.TryGetTarget`, `Load` also treats `IOException` / `UnauthorizedAccessException` as "unreadable" and returns null (the marshaller turns `0x80070002` into `FileNotFoundException`). (2) `FolderScanner` caches the path a shortcut points to by the `.lnk` modified time, and each scan re-reads only the target's timestamp; a target on the network (UNC or a network drive) has no timestamp read (treated as `default`). (3) `ConfigStore.Open` retries reading 4 times (250 ms apart) on `IOException` / `UnauthorizedAccessException` and throws only if it still fails, never falling back to defaults. (4) The `InstanceChannel` listen loop catches all exceptions and continues; `App` logs `AppDomain` / `TaskScheduler` unhandled exceptions.
**Reason**: (1) When a `.lnk` is deleted or locked by another program during a scan, the exception is caught by `Scan`'s per-folder catch → the whole widget is missing from the result → `Reconcile` treats it as gone and purges its position and order (reproduced with a test). (2) The scan is on the UI thread, and reading the timestamp of a disconnected network share blocks until the connection times out, once per rescan. (3) At sign-in a virus scan / sync program briefly locking config would crash startup; falling back to defaults would overwrite the real settings. (4) Nobody awaits the listen task, so any exception would silently disable taskbar buttons.
**Alternatives**: Keeping the old scan result when a single folder fails to read (a bigger change; the shortcut handling covers the common causes); reading network targets' timestamps in the background (high complexity, the gain being only that a network shortcut's icon redraws automatically when the target updates).
**Consequences**: A shortcut pointing to a network location doesn't redraw its icon automatically after the target updates (restart needed). A single folder failing to read for other reasons still temporarily vanishes from the scan.
**Author**: The user asked (/goal), the implementation was decided by me
