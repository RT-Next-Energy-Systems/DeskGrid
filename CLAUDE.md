# DeskGrid

"Phone-style folders" for the Windows 10 (22H2) / 11 desktop: a folder icon shows a 2×2 thumbnail preview of the apps inside; click it to open a grid panel, click outside or press Esc to close it. Every widget maps to a real folder, so changing the folder's contents syncs at once. To be open-sourced under the MIT license, so the code must be clean and maintainable.

> This file and `CLAUDE.zh-TW.md` are twins (English / Traditional Chinese): change both together. See "Language policy" in `AGENTS.md`.

# Tech stack

- C# + WPF, **.NET 10 LTS**, x64 (the original spec said .NET 8; changed to .NET 10 because .NET 8 reaches EOL on 2026-11-10, see `context/decisions.md`)
- Win32 interop: CsWin32; the APIs needed are listed in `src/DeskGrid/NativeMethods.txt`
- No Electron / WinForms / third-party UI frameworks
- Release: self-contained single exe

Common commands:

- Build: `dotnet build DeskGrid.slnx`
- Test: `dotnet test DeskGrid.slnx` (xUnit v3, `tests/DeskGrid.Tests/`)
- Run: `src/DeskGrid/bin/Debug/net10.0-windows/win-x64/DeskGrid.exe`
- Package: `dotnet publish src/DeskGrid/DeskGrid.csproj -p:PublishProfile=win-x64` → `artifacts/publish/DeskGrid.exe` (self-contained single exe, about 62 MB)
- Release: push a `v*` tag (e.g. `v0.1.0`) → GitHub Actions builds a Release with the single exe only (GitHub shows the SHA-256 on the asset; the updater reads the API's `digest`)
- Log: `%LOCALAPPDATA%\DeskGrid\deskgrid.log`; Config: `%APPDATA%\DeskGrid\config.json`

# Architecture

One folder per module, `src/DeskGrid/<Folder>/`, namespace `DeskGrid.<Folder>`.

| Module | Folder | Responsibility |
|---|---|---|
| DesktopHost | `Desktop/` | Mounts widget windows on the desktop icon layer (behind all normal windows); supports both the legacy and the Win11 24H2+ desktop hierarchies; re-mounts automatically after Explorer restarts |
| ConfigStore | `Config/` | `%APPDATA%\DeskGrid\config.json`; stores only widget positions, panel column count, item order, root folder path and drop mode, plus the panel background (added 2026-10-24 with the user's consent), what happens to the items when a folder is deleted (`deleteMode`), whether the user was asked about starting with Windows (`autoStartAsked`, 2026-10-30), whether to check for updates at startup (`checkForUpdatesAtStartup`, default on, 2026-10-30), where panels open (`panelOpenMode`: `nearby` / `centered`, 2026-11-03) and the interface language (`language`: `system` / `english` / `traditionalChinese`, 2026-11-03) |
| FolderScanner | `Folders/` | Root folder defaults to `%USERPROFILE%\DeskGrid\`; every subfolder = one widget; FileSystemWatcher listens for Created/Deleted/Renamed/Changed with a 300 ms debounce; a Renamed event must carry the position and order in config over; a root folder located on the user's desktop is refused with a message |
| IconService | `Icons/` | Gets 256px icons through IShellItemImageFactory; composes the first 4 (by order) into a 2×2 preview; cached, rebuilt only when the folder changes |
| FolderWidget | `Widgets/` | The folder icon + name on the desktop, draggable, position saved (`FolderWidget` view, `WidgetBoard` sync and placement, `WidgetGrid` grid) |
| PopupPanel | `Panel/` | The grid panel (3 columns by default, scrolls beyond that, no paging); clicking an item launches it with ShellExecute; click outside / Esc / losing focus closes it; opens next to the widget or centered on the screen (`PanelOpenMode`) |
| TrayApp | `Tray/`, `Settings/` | Tray menu: new folder, settings, start-with-Windows switch, exit (`TrayIcon`, `AutoStart`; the settings window, change log window and new-folder dialog are in `Settings/`). "Open root folder", "Pin all folders to the taskbar", the GitHub address and the change log are in the settings window (2026-10-30) |
| Drag and drop in | `Folders/ItemImporter` | Files dragged onto a widget become shortcuts / are moved / are copied according to the rules |
| Delete folder | `Folders/FolderDeleter`, `Shell/RecycleBin` | Widget context menu delete: the folder goes to the Recycle Bin, its items first move to the desktop or are deleted with it, per the setting |
| Stack icons into a folder | `Widgets/IconMerger`, `Folders/DesktopFiles` | Drag a desktop icon onto another one → a new folder (during the drag a transparent drop zone takes over Explorer's drop) |
| Taskbar pinning | `Taskbar/` | Widget context menu "Pin to taskbar": builds an `--open "folder"` shortcut for the user to pin; the settings window's "Taskbar" card button "Pin all folders to the taskbar…" builds an `--all` shortcut (the panel lists all folders); clicking it notifies the running DeskGrid over a named pipe (`InstanceChannel`) to open the panel at the cursor; each shortcut carries its own AppUserModelID so the taskbar doesn't merge them |
| Version check | `Updates/` | 8 seconds after startup and from the settings window's "Check for updates" button: looks up the latest GitHub release; a newer version shows an "Update / Keep / Cancel" dialog; Update = download the exe, verify SHA256, and a small PowerShell script swaps the file after the program exits and restarts it |
| (support) Shell | `Shell/` | Shell interop: `ShellImage` (icons), `ShellItem` (open with ShellExecute, display names), `ShortcutFile` (build .lnk), `ShellContextMenu` (Explorer's context menu for files), `RecycleBin` |
| (support) Log | `Diagnostics/` | A simple append-only log |
| (support) DispatcherThread | `Threading/` | A WPF Dispatcher on a dedicated STA thread (for Shell / WPF imaging; tests use it as the UI thread too) |
| (support) Strings | `Resources/` | `Strings.resx` (en, neutral) + `Strings.zh-TW.resx`; the strongly typed `DeskGrid.Resources.Strings` is generated at build time. `UiLanguage` picks the language (settings choice or Windows' language) and switches the whole process |

## DesktopHost notes (measured in stage 1)

- **Mount point**: a widget is an `HwndSource` (`WS_CHILD`, `UsesPerPixelTransparency` → `WS_EX_LAYERED`) whose parent is `SHELLDLL_DefView`, z-ordered above `SysListView32` (the icons) → it receives clicks, sits behind all normal windows, and is still visible after Win+D.
- **Two hierarchies** (both handled by `IconLayer.Find()`, which first sends Progman `0x052C`):
  - New (24H2+, measured on local build 26300): `Progman`[`WS_EX_NOREDIRECTIONBITMAP`] → `SHELLDLL_DefView`[`WS_EX_LAYERED`] → `SysListView32`; plus `Progman` → `WorkerW` (child window).
  - Old (Win10 ~ Win11 23H2): top-level `WorkerW` → `SHELLDLL_DefView` (under `Progman` before the split). **Not yet tested on a real machine.**
- **Must be layered**: on 24H2+ Progman is composition-based and non-layered child windows are not drawn; layered also makes fully transparent pixels click-through.
- **Explorer restart**: when explorer exits, cross-process child windows are destroyed with it → `DesktopSurface.Lost` → `DesktopHost` retries every second, mounting a new `HwndSource` on the new DefView and reusing the same WPF content (state kept). `TaskbarCreated` broadcast is the second trigger (it must be received by a hidden top-level window; a message-only window doesn't get broadcasts).
- **Coordinates**: surface positions are physical screen pixels (`ScreenPoint`), converted to DefView client coordinates when mounting.
- **Multiple monitors** (2026-11-01, user report: "after connecting an external monitor and placing it left of the primary one, all widgets jumped to the left, and a panel opened on the left monitor appeared on the primary one"): the desktop windows (Progman / DefView) cover all monitors; when a monitor is added **left of or above** the primary one their origin moves in the negative direction while the child windows' (surfaces') client coordinates stay the same → the whole batch drifts on screen; `DesktopSurface.Position` (what the config stores and what panel placement uses) didn't change, so the panel opened at the "logical position" = the primary monitor. Fix: `DesktopSurface.Resync()` (`MoveTo` if `GetWindowRect` differs from `Position`), run by `DesktopHost` every second and immediately on `WM_DISPLAYCHANGE` (hidden top-level window). After 1.5 seconds (Explorer has re-laid out) it raises `DisplayChanged` → `WidgetBoard.OnDisplayChanged` (re-read the grid, re-place by the **position stored in config**, close an open panel). A stored position whose center is in no monitor's work area (a monitor was unplugged) → temporarily put in the nearest free cell of the nearest monitor, **without overwriting the stored position**, so it returns when the monitor does (`WidgetBoard.Add` and `OnDisplayChanged`; only dragging stores a new position). Reproduced and verified on a real machine: with `ChangeDisplaySettingsEx` (`DM_POSITION`, `CDS_UPDATEREGISTRY | CDS_NORESET`, then apply with NULL; dm must be NULL when applying) the second monitor was switched between the right of the primary (x=2880) and its left (x=-2360); the Progman rectangle changed from (0,0,5240,1800) to (-2360,0,2880,1800), the log showed "Put 9 surface(s) back", and the 9 surfaces kept their screen coordinates; restored after the test.
- **Layout settings changes** (2026-11-03, issue #21): the hidden top-level window receives `WM_SETTINGCHANGE` whose `wParam` is one of `SPI_SETWORKAREA` (taskbar moved / resized), `SPI_ICONHORIZONTALSPACING` / `SPI_ICONVERTICALSPACING` / `SPI_SETICONMETRICS` (desktop icon spacing), `SPI_SETLOGICALDPIOVERRIDE` (scaling) (`DesktopHost.ChangesDesktopLayout`), and shares the same 1.5-second `DisplayChanged` with `WM_DISPLAYCHANGE`. `WidgetBoard.OnDisplayChanged` now also snaps on-screen widgets to the nearest free cell of **today's** grid and saves (only when the grid follows the desktop icons, `FollowsIcons`; when the icons can't be read they stay where they are). Not verified on a real machine by changing the taskbar / spacing.
- `WS_EX_NOPARENTNOTIFY`: stops a hung Explorer thread from hanging us through parent notify.
- **Software rendering** (2026-11-03, lightweight): the widgets' `DesktopSurface` and the hidden `ShellMessageWindow` set `CompositionTarget.RenderMode = SoftwareOnly`, so no Direct3D device is created before a panel has been opened (measured private 117 → 83 MB; widget screenshots differ from hardware rendering only by edge anti-aliasing ≤ 15/255). The panel keeps hardware rendering: under software rendering the DWM extended frame (Acrylic) can turn black; setting `ProcessRenderMode` for the whole process is not usable. After a panel has been opened the D3D device exists (about +60 MB, which later falls back).

## Config / Folders notes (stage 2)

- **Source of data**: folder contents come only from disk; config only adds what the file system can't store. `WidgetConfig` is keyed by folder name (case-insensitive): `Position` (physical screen pixels, null until placed), `ItemOrder` (list of file names). `PanelColumns` (global, default 3), `DropMode` (move/copy), `RootPath` are global.
- **Items**: the visible files in a widget folder (hidden/system files such as desktop.ini are skipped); subfolders are not items; loose files directly in the root folder are ignored. First order is Explorer's natural sort (`StrCmpLogicalW`), new items are appended, vanished items are removed from the order.
- **Threading**: `FolderScanner` must be created on a thread with a `SynchronizationContext` (the UI thread); all events are posted back to that context in the order they happened, so a rename is always handled before the refresh that follows it. The whole config is accessed only on the UI thread, no locking needed.
- **Rename**: `WidgetRenamed` / `ItemRenamed` transfer the settings and save at once; other changes rescan everything after a 300 ms debounce (the data is small, a rescan is simpler than tracking diffs). Watcher overflow → rescan.
- **Root folder deleted and recreated** (2026-11-03, issue #24): a `FileSystemWatcher` dies with the folder it watches. When the watcher raises `Error`, or the root folder is found missing after the quiet period, `FolderScanner` checks the root folder every second (`_recoveryTimer`); once it is back, the watcher is rebuilt in the UI context and `Changed` is raised. While the root folder is missing a rescan returns `null`, so the settings are not wiped.
- **Shortcut target updated** (2026-11-03, issue #25): `ShortcutTargetWatcher` keeps one watcher (non-recursive; network paths skipped) per folder that holds a shortcut target, and only fires `FolderScanner`'s quiet-period timer when the target's file name is written / created / renamed; after the rescan `TargetWriteTimeUtc` has changed, the icon cache key changes with it and the icon is redrawn. The watcher list is synced after every `Scan`.
- **Purging**: a rescan removes settings of folders/items that no longer exist. When the root folder can't be read (e.g. the disk vanished) it does **not** recompute, so it never clears all settings at once.
- **Writing**: write a `.tmp` file, then rename; a broken config is renamed to `config.json.<time>.bad` and defaults are used.
- **Root folder validation** (`RootFolder.Prepare`): must be a full path, must not be inside the user's or the public desktop, must be creatable. If it fails at startup → a message, then the default is used and written back to config.
- **Later stages**: clamp a loaded position that falls outside the work area (stage 4).

## Icons notes (stage 3)

- **Always icons, never content thumbnails**: `SIIGBF_ICONONLY`; shortcuts take the target's icon, without the arrow overlay. Measured: at 256px the Shell always returns 256×256 (`SCALEUP` makes no difference).
- **Alpha**: the DIB section the Shell returns has **straight (non-premultiplied) alpha** (many pixels measured with RGB > A); build the `BitmapSource` as `Bgra32`; `CreateBitmapSourceFromHBitmap` drops alpha and must not be used. A bottom-up DIB has to be flipped.
- **Threading**: Shell calls and preview composition run on a dedicated STA thread (`DispatcherThread "DeskGrid.Shell"`); results are frozen bitmaps and can cross threads. `IconService` itself is called only on the UI thread (the cache is a plain Dictionary).
- **Cache**: memory only. The icon key = (path, LastWriteTimeUtc, the shortcut target's LastWriteTimeUtc) (`FolderItem.TargetWriteTimeUtc`, which `FolderScanner` reads during scanning with `ShortcutFile.TryGetTarget` from the .lnk target; when a program update changes the icon the shortcut itself is unchanged, so looking only at the .lnk would show the old icon forever; a changed target is redrawn only after the next rescan). What is cached is the `Task`, so simultaneous requests fetch once. The preview key = (path, ticks) of the first 4 items; changes from the 5th item on don't rebuild it. `Retain(widgets)` drops vanished/changed entries on every catalog refresh.
- **Preview layout** (`PreviewComposer`): a 256×256 transparent image, 2×2, 8% gap, filled row by row; fewer than 4 items leave empty cells. The folder's base color is drawn by the widget itself (stage 4).

## Widgets notes (stage 4)

- **Look** (chosen by the user): a 48 DIP light translucent rounded square (white 30%, corner radius 22.37%) containing the preview, with the name below in the system icon font, white text with shadow, up to 2 lines; when the mouse is over it the whole cell gets a faint white highlight (like a native icon).
- **Cells**: one cell = one native desktop icon cell (`DesktopIconGrid` sends `LVM_GETITEMSPACING` / `LVM_GETITEMPOSITION` to Explorer's `SysListView32`; the positions have to be read across processes, hence `VirtualAllocEx` + `ReadProcessMemory`); a widget is exactly one native icon cell in size (no integer multiples, otherwise at high DPI 76×96 DIP would be a bit bigger than a 150×182 px icon cell and become twice as big). The grid is anchored on the first native icon's cell, so it aligns with the desktop icons; each column fills top to bottom, columns from right to left. When it can't be read, fall back to the old behavior (starting at the work area's top right, 76×96 DIP). Every widget sits on a cell, one per cell.
- **Avoiding native icons**: a cell that overlaps a native icon cell by more than 1/4 is not used (`WidgetGrid` obstacles / `Covers`), unless no other cell is left. The widget does the avoiding when placed / when a drag is released. Order of choice (`WidgetGrid.Candidates`, fixed 2026-11-06): a cell with neither a widget nor an icon → a cell without a widget (under an icon) → any cell; a widget's cell is never shared while one without a widget is left.
- **Icons give way** (chosen by the user, 2026-10-28): if a native icon later lands on a widget cell (Explorer puts a new shortcut in a cell it thinks is empty, or the user drags an icon over), `WidgetBoard.ClearIconsOffWidgets` moves that icon to the nearest free cell (`LVM_SETITEMPOSITION`, coordinates in lParam, no need to write into Explorer's memory). When the desktop has "Auto arrange icons" on (the list view has `LVS_AUTOARRANGE`) icons can't be moved, so the widget gives way instead.
- **Detecting icon changes** (`DesktopIconWatcher`): `SetWinEventHook` only on the desktop's Explorer thread (unlike the taskbar), out-of-context, no polling. The list view's `EVENT_OBJECT_CREATE/DESTROY/REORDER` = added / deleted; **moving an icon raises no list-view event at all** (measured, including `LVM_SETITEMPOSITION`), so that thread's `EVENT_SYSTEM_CAPTUREEND` (raised at the end of every desktop drag) is used. After a 300 ms debounce the cells are re-read. Releasing with the cursor over a widget = a drop onto the widget (adds to the folder), not an overlap.
- **Placement**: with a saved position → snap to the nearest free cell; none saved → the primary monitor's first free cell (widgets with saved positions are handled first, so a new widget doesn't take their cells). The result is written back to config (not written if unchanged).
- **Rubber-band selection and dragging together** (2026-11-03, issue #26, user chose "select with the rubber band and drag together"): Explorer draws the rubber band and selects its own icons itself; `MarqueeSelector` only reads the mouse: on `DesktopPressed` (`EVENT_SYSTEM_CAPTURESTART`), if the left button is down and the cursor is not on any desktop icon cell, it looks at the cursor every 20 ms, and once past the drag distance it takes the rectangle from the press point to the cursor (`ScreenRect.Between`) and `WidgetBoard.SelectWithin` selects the widgets whose picture + name area (the cell inset 15% left/right and 10% top/bottom, `WidgetGrid.IconArea`) intersects it (`FolderWidget.IsSelected`, faint white background). Any desktop press or a click on a widget clears the selection; dragging a selected widget → `Entry._group` is the whole selection, which moves together, cancels together on Esc, and on release snaps and saves one by one (deleting by Recycle Bin only for a single widget); dragging an unselected widget first clears the selection. Ctrl+A / Ctrl add-to-selection are not done. **Not verified on a real machine at all** (a desktop rubber band can't be operated).
- **"Show desktop icons" off** (2026-11-03, issue #23): measured (a probe script started by explorer sends `WM_COMMAND 0x7402` to DefView): Explorer only hides `SysListView32`; DefView and our surfaces are untouched, so widgets used to stay. Now `DesktopHost` checks the list view's `IsWindowVisible` every second and, when it changes, calls `SetVisible` (`ShowWindow` `SW_HIDE` / `SW_SHOWNA`) on all surfaces; newly mounted surfaces also get the current state.
- **Esc cancels a drag** (2026-11-03, issue #22): a widget that isn't activated gets no keyboard events, so during a drag `FolderWidget` watches `GetAsyncKeyState(VK_ESCAPE)` with a 30 ms `DispatcherTimer`; on Esc it releases the mouse capture and raises `DragCancelled` (the following mouse release is ignored, triggering neither a click nor `DragCompleted`), and `WidgetBoard` moves the widget back to `_dragOrigin` (already the saved cell, no snapping / saving needed).
- **Dragging**: `FolderWidget` only turns the mouse into Clicked / DragStarted / Dragged(cursor displacement, physical pixels) / DragCompleted; it counts as a drag only beyond the system `SM_CXDRAG`. During the drag it follows the cursor freely; on release it snaps to the nearest free cell (target cell taken → the next nearest free cell) and saves.
- **Lifecycle**: `WidgetBoard.Show` matches by folder name: vanished ones are removed, new ones created, existing ones get a new name and preview. A folder rename = the old widget removed, the new widget created at the transferred position.
- **DesktopHost**: `Add` mounts at once when an icon layer exists (the last found DefView is cached, checked with `IsWindow`), `Remove` destroys the window; if creating the child window fails (`Win32Exception`) → enter retry.
- **Context menu**: "Pin to taskbar…", "New folder…", "Delete folder…".
- **No activation stealing**: `DesktopSurface` answers `WM_MOUSEACTIVATE` with `MA_NOACTIVATE`. Otherwise clicking a widget would activate the Explorer desktop, and Explorer swallows that activating click (a widget wouldn't receive the press while a panel is open).

## Panel notes (stage 5)

- **Look** (chosen by the user): opens beside the widget (below → above → left → right, the first that fits; the other axis is clamped back into the work area); items are 48 DIP icons in 76×96 DIP cells; the folder name on top; at most 4 rows shown, beyond that it scrolls (thin scroll bar).
- **Where it opens** (2026-11-03, config `panelOpenMode`, settings "Where a folder opens"): two modes. **Nearby** (`PanelOpenMode.Nearby`, default) is the behavior above: next to the widget, as big as its items need (up to 4 rows). **Centered** (`PanelOpenMode.Centered`) puts every folder's panel in the middle of the work area of the widget's monitor (`PanelPlacement.Center`), always at the **same size** whatever the folder holds, so panels don't differ in place or size: `columns` wide and `columns` rows high (a square; fewer rows only when the monitor's work area is too short, `PopupPanel.FixItemsSize`), the items scrolling inside (the scroll bar's room is always reserved so it never widens the panel; an empty-folder hint shares the items' cell so an empty folder is just as tall; `MakeRoomForIncoming` does not resize). The list of all folders is the same size. A panel opened by holding a drag over a widget (`OpenForDrag`, not activated) is **always nearby** whatever the setting: the cursor can't travel across the screen to a centered panel without the drag counting as having left it. The setting is read when a panel opens (`PanelController.Open`). Not verified on a real machine (unit tests check the sizes and the position math).
- **Background is customizable** (config `panelBackground`): `system` (default; Win11 22H2+ system Acrylic + the system light/dark theme; opaque system colors on other versions), `dark`, `light` (translucent), `custom` (`customColor` #RRGGBB + `customOpacity` 0–1; the text color is black/white automatically from the background's brightness). The settings UI came in stage 6; at that point it took a hand edit of config and an app restart.
- **How Acrylic is done** (measured): a borderless `WS_POPUP` window gets **no** DWM system backdrop; the frame has to stay: `SingleBorderWindow` + `WindowChrome(GlassFrameThickness=-1, CaptionHeight=0)` + remove `WS_SYSMENU` (otherwise DWM draws a close button in the extended frame) + transparent composition background + `DWMWA_SYSTEMBACKDROP_TYPE=TRANSIENTWINDOW`, `DWMWA_WINDOW_CORNER_PREFERENCE=ROUND`. **Do not use `SizeToContent`** (WPF adds the frame size that WindowChrome removed) → measure the content yourself, then set Width/Height. Non-Acrylic styles use a layered window (`AllowsTransparency`) and draw the rounded background themselves.
- **Stays on the side it opened on** (2026-10-31): `PanelPlacement.Side` is chosen only the first time it is placed (and when a different folder / the list is shown); afterwards growth (a row added by `MakeRoomForIncoming` during a drag-in, a rescan after the drop) is clamped back into the work area on the same side (it may cover part of the widget). Otherwise, with the widget at the bottom of the screen, growing taller no longer fits → jumps to the right → the cursor is not inside the panel → DragLeave closes it → it fits again and returns below → endless back and forth = severe flicker (user-tested, confirmed by the log).
- **Multiple monitors** (2026-11-01): the panel is placed in the work area of the monitor containing the widget's center, and positions and sizes are always converted with **that monitor's** DPI (`Reposition(window, size)` always takes the size). When a window is created on a monitor with another DPI and then moved by `SetWindowPos`, Windows sends `WM_DPICHANGED` with a suggested position and size scaled from the old size, and WPF accepts them → on receiving it `OnWindowMessage` calls `Reposition` again with `_size` (the wanted size in DIPs; `Width`/`Height` can't be trusted, WPF has already changed them).
- **Positioning**: in `SourceInitialized` (before the first show) with physical-pixel `SetWindowPos`, so it never flashes elsewhere; repositioned after content changes (live refresh). Resizing always does `SetWindowPos` with the new position + size first and then sets the WPF size (`Resize`): growing first and moving afterwards leaves the part that was off screen unpainted when the panel hugs the bottom of the screen, cutting off the last row's names.
- **Closing**: Esc, losing activation (click outside), after an item is launched, clicking the same widget again; clicking another widget switches directly. **Screenshot exception** (`ScreenCapture`): when it loses focus and the foreground is the Windows screenshot tool (`SnippingTool`, Win10 `ScreenClippingHost`) it doesn't close, but hooks `EVENT_SYSTEM_FOREGROUND` and waits until the foreground leaves the screenshot tool; coming back to the panel is normal, going elsewhere closes it. Only one panel at a time. The panel updates live when the folder's contents change, and closes when the folder is gone.
- **Launching**: `Process.Start(UseShellExecute=true)` (i.e. ShellExecuteEx), working directory = the item's folder (a shortcut's own working directory takes priority), `ErrorDialog=true` so Windows shows its own error (e.g. the shortcut target doesn't exist); exceptions such as a cancelled UAC are only logged.
- **Names**: item names use the Shell display name (`SIGDN_NORMALDISPLAY`, same as File Explorer: `.lnk`/`.url` show no extension, others follow the user's "hide extensions" setting).
- A Button's theme style forces black text; the item style must bind explicitly back to the window's `Foreground`.
- **Dragging inside the panel**: an item dragged beyond the system drag distance starts OLE `DoDragDrop` (`FileDrop` + the custom formats `DeskGrid.PanelItem` / `DeskGrid.PanelFolder`). Dropped back into the same panel → reorder (`WidgetCatalog.MoveItem` changes `ItemOrder`); dropped on the desktop / a folder → handled by the other side (Explorer moves the file); dropped on another widget → `ItemImporter` always "moves" files under the root. The panel does not close when it loses focus during a drag; after it ends it closes if the cursor has left.
- **Drag-out detection**: whether the cursor is inside the panel is always compared with `GetWindowRect` in physical pixels (a DIP conversion would count a cursor that has just left the right / bottom edge as inside). `PopupPanel`'s `_watch` (a 50 ms DispatcherTimer, `OnWatch`) watches the cursor, not just `DragLeave`: only when the cursor has been away from the panel **and its widget** (`_anchor`) for more than 300 ms does it count as dragged out (`TakeOut`), so moving across the gap from the panel to the widget doesn't close it. A rescan during a drag (`PopupPanel.Refresh`) is deferred until the release; the item's cell stays hidden until the shadow lands, even if it is rebuilt (`_settlingItem`).
- **List of all folders** (`ShowList`, taskbar `--all`): the cells are folders (base tile + 2×2 preview, `PanelItem.Folder`); one click calls `ShowFolder` in the same window, with a ← at the left of the title back to the list; list mode can be reordered by dragging (since 0.2.1) and cannot be renamed; **it accepts files dropped on a folder cell** (2026-11-03, issue #11: `FolderUnder` finds the cell under the cursor, `TintDropTarget` colors it via the button's `Tag` [the template's Border background binds to it], and on release → `ItemsDropped(folder name, paths, the folder's current item count)`, with the same import rules as dropping on a widget).
- **Re-measuring**: after the content changes, `UpdateLayout()` must run before measuring the panel size (`MeasureContent`) — replacing `ItemsSource` only marks the WrapPanel, and a direct `Frame.Measure` would return the old size.
- **Where a taskbar-opened panel appears** (2026-11-03, issue #13 / #12): the second process reads the cursor as the first thing in `OnStartup` (`OpenMessage`: one line `x TAB y TAB name` written into the named pipe), and the panel opens at the position **at the moment of the click**, not at the moment the request arrives (about 1 second later); when the first process is started with `--open` it likewise reads it at startup. A pinned folder that has been deleted → open the "all folders" list (it used to be only logged).
- **Taskbar panel hugs the taskbar** (2026-11-03, issue #27): the anchor is the cursor (on the taskbar, outside the work area); the panel's bottom edge used to be cursor Y − gap, so how far it floated above the taskbar depended on where in the button the cursor was ("occasionally"). `PanelPlacement.Within` first clamps the anchor into the work area, then computes; the panel is always "1 px + gap" from the work area's edge. **The issue's screenshot was not seen**; this cause was deduced from the description and the code, and awaits the user's confirmation.
- **Dragging an app from the Start menu** (2026-11-03, issue #19): an app has no file path; the drag data has only `Shell IDList Array` (CIDA) and no `FileDrop`. When there is no `FileDrop`, `DroppedItems.Read` extracts the absolute PIDLs with `ShellIdList.Parse`, and for items that aren't files / folders (`ShellItem.Describe`: `SIGDN_FILESYSPATH` unavailable) builds a temporary `.lnk` with `ShortcutFile.CreateFromIdList` (`IShellLink.SetIDList`) in `%TEMP%\DeskGrid\drops\<guid>\` (named after the display name); after that it is the same as a normally dropped shortcut (copied into the folder), and `Dispose` deletes the temporary files. All three drop sites (`WidgetBoard.ImportDropped`, `PopupPanel`'s folder panel and list) use it; the cursor effect shows link (copy if the source doesn't offer it). The tests walk the whole path with the virtual "This PC" item; **nothing was actually dragged from the Start menu**, so the data format Start really offers (whether `Shell IDList Array` is there, whether the PIDL is an AppsFolder item) is unverified.
- **Taskbar button pressed again = close**: clicking the taskbar first makes the panel lose focus and close; the request from the same click arrives from the pipe afterwards. When closing with `Shell_TrayWnd` as the foreground, `PanelController` remembers which panel it was, and within 3 seconds a taskbar request for the same panel counts as "close" and does not reopen it.
- **Drag animation** (iOS style): `DragGhost` is a click-through topmost layered window (a pure Win32 window + `UpdateLayeredWindow`, **do not use `HwndSource`**: WPF draws into it too, ULW fails → black square) that carries the icon with the cursor (position updated on every `QueryContinueDrag`, brought to the top again when a newly opened panel covers it); the original cell is left empty (container `Opacity=0`), and the other items slide to their new cells with a `TranslateTransform` animation (`PopupPanel.Slide`). Dragged away from the panel, the gap closes; after the drop the shadow flies to the cell, or shrinks and fades out when taken elsewhere. The drag event `DragLeave` bubbles up from child elements, so whether the cursor really left the window has to decide.
- **A drag held over a widget opens its panel**: holding a drag over a `WidgetBoard` widget for 550 ms (when the drag can be dropped there, or is an item dragged out of **that folder's** panel, `PanelDragData.IsFrom`) → `DragHovered` → `PanelController.OpenForDrag` (not activated). The original panel is only `HideForDrag` (DWM cloak) and closes when the drag ends, because `DoDragDrop` runs inside it (the controller remembers it in `_dragSource`). Dragged back to the original folder's widget → the original panel `ShowAgainForDrag` (uncloaked, the original cell left empty) so the item can be put back. Dropping into the open panel: `ItemsDropped` → `ItemImporter.ImportTo` → `WidgetCatalog.PlaceNewItem` (a rescan first, so a position can be given); the panel opens a gap before the drop. The widget's DragLeave also bubbles up from child elements; `FolderWidget.IsCursorOver()` decides whether it really left, so the timer doesn't keep restarting. **It must use `WindowFromPoint` == the widget's own HWND**, not just a rectangle comparison: an open panel covers the widgets below it, and with a rectangle comparison a covered widget thinks the cursor is still over it and, when the timer fires, swaps the panel for its own; two panels switching back and forth = severe flicker (user report 2026-10-31).
- **A panel opened by a drag closes by itself** (2026-10-31, `OnWatch`'s `_followsDrag`): while dragging, cursor away from the panel and widget for more than 300 ms → close; mouse released (left or right button) and still nothing dropped in after 250 ms (`TookDrop`) → close; something dropped in → `Activate()`, and when Windows won't give focus (the source is another app, e.g. Explorer) it waits for "a mouse press outside the panel and widget" before closing (Esc has no effect then). When the drag source is our own panel, `DragFinished` decides directly: activate if something was dropped in, close otherwise.
- **Whole widget cell is clickable and droppable**: `Highlight` is normally a background with alpha=1 (invisible but hit-testable); otherwise a release on a transparent part of the cell would fall through to the Explorer desktop, be taken as "an icon dropped on a widget" and be pushed away. While a widget is dragged, `DesktopSurface.BringToFront()` lets it pass over the other widgets.
- **Right-click in the panel** (2026-10-30): a file item → `ShellContextMenu` (`IShellItem.BindToHandler(BHID_SFUIObject)` gets the `IContextMenu`, `QueryContextMenu` fills the native menu, `TrackPopupMenuEx` shows it, `InvokeCommand` with `CMINVOKECOMMANDINFOEX` executes). It is the **classic** menu (the one behind Win11's "Show more options"); there is no public API for Win11's compact menu. (2026-11-03, issue #14: a WPF copy of the compact menu was built and then removed at the user's request, because what is wanted is Explorer's own menu, not an imitation; do not rebuild a copy.) `CMF_CANRENAME` is not passed (renaming needs an Explorer view to edit in, which isn't here); `CMF_EXTENDEDVERBS` only when Shift is held. Submenus such as "Send to" and "Open with" and owner-drawn items rely on `IContextMenu2/3`'s `HandleMenuMsg(2)`, with `WM_INITMENUPOPUP` / `WM_DRAWITEM` / `WM_MEASUREITEM` / `WM_MENUCHAR` forwarded by an `HwndSource.AddHook`. While the menu and the command run, `_menuOpen` is true and `Deactivated` doesn't close the panel (a delete confirmation or a properties window steals activation, and the panel must outlive the command); afterwards, if the panel is no longer the foreground it closes. `ShellContextMenu` does not `ReleaseComObject` the menu objects (left to the finalizer), because "Properties" and "Open with" may still use them on another thread after `InvokeCommand` returns. A folder cell (list of all folders) and the name bar's right-click → our own WPF menu (New folder… / Delete folder…); after the press the panel closes first and then raises the event (both ask a question).
- **Arrow-key navigation** (2026-11-03, issue #20): `PopupPanel.OnKeyDown` uses `PanelNavigation.NextSlot` (a pure function with unit tests) to decide the target cell for the arrow keys / Home / End (stops at the edges, no wrap-around; with no selection ↓→Home goes to the first cell, ↑←End to the last; with a shorter last row ↓ goes to the last cell), then `Focus()` + `BringIntoView()` on that cell's `Button`. Enter / Space are triggered by the Button itself. Not intercepted while the title text box has focus.
- **Esc closes a drag-opened panel that can't get focus** (2026-11-03, issue #9): `OnWatch`'s `_awaitsClick` phase (after something is dropped in and Windows won't give focus) also watches `GetAsyncKeyState(VK_ESCAPE)` besides "a mouse press outside the panel and widget". An Esc during a drag is handled by the OLE drag source (Explorer) itself as cancelling the drag. Not verified on a real machine by dragging from Explorer.
- **Renaming from the title**: hovering the panel title shows a pencil (Segoe MDL2 `E70F`); a click turns it into a text box; Enter / losing focus confirms, Esc cancels. `App.RenameFolder` validates (`WidgetFolderName.Validate`) and then `Directory.Move`s; a case-only change goes through a temporary name (`Directory.Move` refuses the same name); on success the panel first changes its own `Folder` to the new name, so the rescan that follows doesn't fail to find it and close.

## Drag and drop in / Tray / Settings notes (stage 6)

- **Drop rules** (`ItemImporter.Plan`, chosen by the user): `.exe` → build a `.lnk` (never move or copy the exe itself); a `.lnk`/`.url` **directly on** the user's or public desktop → per `DropMode` (default move); a `.lnk`/`.url` anywhere else → always copy; ordinary files and folders → build a `.lnk`; already inside that folder, or dragging that folder itself / a parent → ignored. A duplicate name gets " (2)" automatically. A public-desktop shortcut that can't be moved for lack of permission → copied instead.
- **Shortcut naming**: an exe uses the file name (`notepad.exe` → `notepad.lnk`), others keep the full name (`report.pdf.lnk`), a folder uses the folder name, a drive root what is left of the path without the characters a file name can't have (`D:\` → `D.lnk`; it used to become `D:\.lnk`, a path, so the shortcut landed at the drive's root, fixed 2026-11-06); working directory = the target's folder.
- **Drop wiring**: `FolderWidget` only provides `AllowDrop` and the highlight during a drag; `WidgetBoard` handles `DragOver` (the cursor shows the effect of the first item that can be handled: move / copy / link) and `Drop`. The file operations are done by us, and we report **Copy, never Move** to the source, otherwise the source would delete the original. OLE drops reach the cross-process child windows under Explorer (tested with an OLE drag).
- **Dark mode for native menus** (2026-11-03, issue #18): `Shell/MenuTheme` calls uxtheme's `SetPreferredAppMode(AllowDark)` / `FlushMenuThemes` by ordinal 135 / 136 (undocumented APIs, obtained through CsWin32's `LoadLibrary` + `GetProcAddress`; not done before Windows 10 1903), called before the tray menu and the panel item context menu are shown each time; a missing function keeps the menu light. The test `MenuThemeTests` confirms on this Win11 machine that the ordinals exist; **it was not visually confirmed that the menu really turns dark**. The settings window already follows system dark mode (Fluent).
- **Tray** (`TrayIcon`): `Shell_NotifyIcon` + `NOTIFYICON_VERSION_4`, both left and right click open a native Win32 menu (rebuilt every time, so the check states are current); menu actions run after the menu closes (they may open modal windows); the icon is re-added on `TaskbarCreated`. The icon is loaded with `LoadIconMetric` from the exe's `#32512` (`<ApplicationIcon>`) → **the manifest must declare Common Controls v6**.
- **Start with Windows** (`AutoStart`): `HKCU\...\Run\DeskGrid = "exe path" --autostart`; when Task Manager's "Startup apps" disables it, a flag is left in `StartupApproved\Run` (first byte odd) → treated as off; when we toggle, we clear that flag. If at startup the exe was moved or the old entry has no `--autostart`, it is updated.
  - **Boot flow** (2026-10-30): a start with `--autostart` first runs `DesktopHost.WaitUntilSettledAsync` (`DesktopReadiness`; every 0.5 s on a background thread it reads the desktop icon positions, and two equal reads in a row count as ready; on timeout, 45 s, it goes ahead anyway) before building the widgets. When the user starts it themself the desktop is certainly ready, no waiting. Reason: at sign-in the list view already exists but the icons aren't laid out, the grid has no anchor → widgets get snapped to the fallback grid and written back to config, overwriting the real positions. `WidgetBoard.Add` has another safeguard: when the icon grid can't be read (`WidgetGrid.FollowsIcons` false), a widget with a saved position is neither snapped nor saved.
  - **First run**: when config `autoStartAsked` is false, once the widgets appear it asks once "start with Windows?" (users who already enabled it are marked silently); after that it can only be toggled from the tray menu. When the registry write is refused (group policy) `ReportAutoStart` shows a warning.
- **Single instance**: the `Local\DeskGrid.SingleInstance` mutex; the second instance just exits.
- **Settings window**: language (*Follow Windows* / *English* / *繁體中文*, config `language`; applied with OK to the whole process at once, `UiLanguage.Apply`, so windows and menus opened afterwards use it), root folder (`OpenFolderDialog`; the "Open" button next to it opens the path in the box in Explorer, and tells the user if the folder doesn't exist), column count 1–8, where a folder opens (nearby / centered, config `panelOpenMode`), the drop mode for desktop shortcuts, the delete mode, the panel background (a custom color uses comdlg32 `ChooseColor`), the "Taskbar" card (the `PinAllFolders` callback → `App.PinAllFoldersToTaskbar`), version / check for updates (including the "check for updates at startup" checkbox), the GitHub address (`UpdateChecker.RepositoryUrl`), the "Privacy" link (resource string `SettingsPrivacyUrl`, pointing at the README's privacy section in the interface language; renaming the README heading means updating it too) and "Change log…" (`ChangeLogWindow`, whose content is the `CHANGELOG.md` (English) or `CHANGELOG.zh-TW.md` (Traditional Chinese interface) built into the exe, chosen by the resource string `ChangeLogResource`; in the csproj `<EmbeddedResource LogicalName=… WithCulture="false">` — without `WithCulture="false"` MSBuild treats `.zh-TW.md` as a satellite assembly resource; `ChangeLog.Parse` only understands `##` / `###` / `- `; **maintain both files together**, `ChangeLogTests` checks that versions and item counts match). The cards sit in a `ScrollViewer`, the window's `MaxHeight` = the work area's height, so on a short screen they scroll while OK / Cancel stay fixed at the bottom. Non-modal, OK / Cancel; **`IsCancel` on a non-modal window does not close it automatically**, call `Close()` yourself. A changed root folder → rebuild the catalog and widgets; other settings → save and close any open panel.
- **Fluent windows** (settings, new folder, update): `ThemeMode="System"`; the card styles `Card` / `CardTitle` are in `App.xaml`; `FluentWindow.UseOpaqueBackground` turns Mica off for an opaque background color so text can use ClearType.
- **XAML must not reference types of this assembly** (e.g. `x:Static` to `Strings`): `Strings` is generated in `obj/` only at build time, and WPF's temporary markup assembly can't compile against it. Interface texts are set in code-behind.
- **App icon**: `tools/make-icon.ps1` generates `src/DeskGrid/Assets/DeskGrid.ico` (multi-size PNG ICO).

## Interface language (2026-11-03)

- **Two languages, user's choice**: English and Traditional Chinese. Settings "Language": *Follow Windows* (default; Traditional Chinese when Windows' UI language is zh-TW / zh-HK / zh-MO / zh-Hant, English otherwise — Simplified Chinese and everything else get English), *English*, *繁體中文*; config `language`.
- **How it switches**: `UiLanguage.Apply(AppLanguage)` sets `CultureInfo.DefaultThreadCurrentUICulture`, the current thread's `CurrentUICulture` (so WPF's own texts, e.g. a text box's Cut / Copy / Paste from the `zh-Hant` satellite, follow too) and `Strings.Culture`; it runs at startup right after the config is loaded and again in `App.ApplySettings`. Texts are looked up when a window, menu or dialog is built, so what opens afterwards speaks the new language; widgets show folder names only, and a widget's right-click menu, which lives as long as the widget, sets its texts again each time it opens (`FolderWidget.LocalizeMenu`, 2026-11-06; it used to keep the language it was made in); an open panel is closed on OK. `UiLanguage` remembers Windows' own UI culture (read before the first `Apply`) so "Follow Windows" can be chosen again later.
- **Policy** (details in `AGENTS.md`, "Language policy"): every UI text lives in `Strings.resx` + `Strings.zh-TW.resx` (`UiLanguageTests` checks key and placeholder parity); never cache `Strings.X` in a `static`; the change log (`ChangeLogResource`) and privacy link (`SettingsPrivacyUrl`) follow the language; **every version-controlled Markdown file exists as `NAME.md` (English) + `NAME.zh-TW.md` (Traditional Chinese) with the same structure** (`MarkdownPairsTests`).
- Windows' own dialogs shown from the UI thread (the color picker, the folder picker, a `MessageBox`'s buttons) take their language from the thread: `UiLanguage.Apply` calls `SetThreadPreferredUILanguages` for the UI thread ("Follow Windows" clears it; the test `WindowsDialogLanguageTests` checks `GetThreadUILanguage`). Entries other programs add to Explorer's context menu keep Windows' language. Not seen on screen: the color picker in the other language.
- Not verified on a real machine: switching in the running app (the unit tests cover the language resolution, key parity and the document pairs).

## Version check and update

- **Source**: `https://api.github.com/repos/Ryan970714/DeskGrid/releases/latest` (anonymous, the 60 per hour limit is enough); drafts and prereleases are skipped; the tag minus `v` is compared with the assembly version (csproj `<Version>`) by major.minor.build. The exe asset is found by the suffix `-win-x64.exe` (the old v0.1.0 asset was called `DeskFolders-…`), the checksum file is `<exe name>.sha256`.
- **Three choices**: Update (download → verify SHA256 (taken from the API `digest` field of the release asset) → `apply-update.ps1` waits for this process to end, then `Move-Item` overwrites the exe and starts it; only the published single-file exe can do this, `UpdateInstaller.CanReplaceSelf`; a development build or a folder that can't be written opens the release page instead), Keep (config `skippedUpdateVersion` records that tag, automatic checks stop reminding, a manual check still shows it), Cancel (stores nothing, reminds again at the next start).
- **Triggers**: one automatic check 8 seconds after startup (a network failure is only logged, no disturbance); the settings window shows the current version and a "Check for updates" button, with the result text beside the button.
- **Can be turned off** (2026-10-30, the SignPath Foundation terms require network behavior to be disclosed and switchable): the settings window's "Check for updates when DeskGrid starts" (config `checkForUpdatesAtStartup`, default on). When off, DeskGrid never goes online by itself; it contacts GitHub only when the user presses "Check for updates" or chooses "Update". The README's "Privacy" lists all network behavior; add to it whenever a network behavior is added.

## Deleting folders and stacking icons into a folder (stage 8)

- **Delete** (`App.DeleteFolder`): widget context menu "Delete folder…" → confirmation dialog → `FolderDeleter.Delete`. The folder itself always goes to the Recycle Bin (`Shell/RecycleBin`, `SHFileOperation` + `FOF_ALLOWUNDO`; when it can't go to the Recycle Bin the shell asks first, `FOF_WANTNUKEWARNING`). Config `deleteMode` (settings window): `moveToDesktop` (default; first moves the visible files and subfolders to the user's desktop, a duplicate name gets " (2)") / `deleteItems` (goes to the Recycle Bin together with the folder). A subfolder that has to go to another drive (the root folder on D:, the desktop on C:; `Directory.Move` can't) is copied whole and then deleted (`FolderDeleter.CopyThenDelete`; a failed copy is removed again and the original stays, 2026-11-06). If any item can't be moved → **the folder is not deleted** and the reason is shown. The desktop widget is removed by the scanner's Deleted event, and leftover config is purged by `Reconcile`, no extra handling needed.
- **Stacking icons** (`Widgets/IconMerger`, chosen by the user 2026-10-29): dragging a desktop icon onto another desktop icon → a new folder (named by `WidgetFolderName.Suggest`) takes the place of the icon dropped on and contains both (`WidgetBoard.MergeIcons` → `ItemImporter.Import`, same rules as dragging onto a widget). Explorer itself treats "dropped on another shortcut" as "open with it", so we have to catch the drop during the drag:
  - **Detection**: `DesktopIconWatcher`'s WinEvent range adds `EVENT_SYSTEM_CAPTURESTART` (0x8; measured: a single click on a desktop icon yields 0x8 / 0x9 in order) → `DesktopHost.DesktopPressed`. `IconMerger` reads the icon cells at the moment of the press (it continues only if the cursor is inside an icon cell), then every 20 ms looks at the left button (`GetAsyncKeyState`; the right button when the buttons are swapped) and at whether the displacement exceeds `SM_CXDRAG`; only then does a drag count as started; 500 ms after the release the drop zone is removed.
  - **Drop zone**: **only one**, a transparent `DesktopSurface` (a `Border` with `AllowDrop` and background alpha=1) that follows the extent of the icon under the cursor (from the top of the icon cell to the bottom of the icon picture; the name below is left to Explorer); with the cursor on no icon it parks off screen (-30000). One window per icon doesn't work: measured, mounting one `HwndSource` on the desktop takes about 26 ms, so 40 icons would freeze for about 1 second. Measured (real Explorer): a drop zone with alpha=1 is **invisible but hit by `WindowFromPoint`**, while with alpha=0 clicks pass through, so 0 cannot be used.
  - **Icon → file**: `LVM_GETITEMTEXTW` (cross-process, `DesktopIconGrid.ReadNames`, sharing `RemoteBuffer` with reading positions) gets the name under the icon, and `DesktopFiles.ByDisplayName` maps it to a file on the user's / public desktop (names use `ShellItem.GetDisplayName`, as in Explorer); a duplicate name (on both desktops, or colliding once extensions are hidden) is not mapped and that icon accepts no stacking. Virtual icons such as This PC and the Recycle Bin can't be mapped to files and accept nothing either. A **real folder** on the desktop doesn't accept it either (Explorer's original "drag into the folder" is kept).
  - **No Explorer calls inside drag callbacks**: DragEnter / DragOver / Drop come in as synchronous RPC from Explorer's OLE loop, and sending messages to Explorer's list view then may deadlock. So the icons are read at the press / when the drag starts, and the callbacks use only the data already read.
  - **Position**: the new folder's config position is first set to the cell of the icon dropped on, then the items are imported; later, when the scanner sees the folder, `WidgetBoard.Add` snaps it to the nearest free cell (the icon moved away = exactly that cell; not moved [copy mode, non-shortcut] = the nearest free cell beside it).
  - The effect reported to the source is always Copy (as for dragging onto a widget); if not a single item was added → the just-created empty folder is deleted and None is reported.
- **No "New folder" tile on the desktop any more** (the user asked for its removal, 2026-10-29): a new folder comes from the tray's "New folder…" or from stacking icons; the former "drag files onto the tile to create a folder" is replaced by stacking icons, and config's `addTilePosition` was removed (an old value in config is ignored on load).
- **Dragging a widget to the Recycle Bin** (2026-10-30): `WidgetBoard.Entry`'s `DragCompleted` first asks `IsOverRecycleBin` (the desktop icon cell under the cursor `DesktopIconGrid.IconAt`, with the name under the icon = `RecycleBin.DisplayName`, i.e. the Shell display name of `::{645FF040-…}`, which follows the display language and renames). If so → the widget returns to the cell it was dragged from, and then `Dispatcher.BeginInvoke` raises `DeleteRequested` (the existing "Delete folder…" confirmation, asked outside the mouse-event handler). Verified on a real machine (in a process started by explorer): the name `資源回收筒` matches the desktop icon and only hits with the cursor on the icon; no drag was actually performed (the computer-use permission can't drag). **Note**: reading Shell names from the Claude desktop app's PowerShell gives English (the process UI language differs), so they can't be used for comparison.
- **Dragging a widget while a panel is open**: `WidgetBoard.WidgetDragStarted` → `PanelController.Close()` (the panel used to stay at the widget's old place).
- **Tests don't run in parallel**: test classes that show windows / menus / fetch Shell icons are in `ShellCollection` (not parallel): only one menu can exist at a time (a second closes the first), and another test's window would steal activation and make a panel close.
- **Test caveat**: a process started from the Claude desktop app (MSIX), `dotnet test` included, **cannot mount a window under the Explorer desktop** (`HwndWrapper` creation fails, error code 0), so `DesktopSurface` / `IconMerger` can't be written as unit tests; to verify desktop behavior, add temporary probe code in a real DeskGrid process (started with `explorer.exe <exe>`) and read the log.

# Behavior rules (must follow)

# Way of working

- Use Git; commit once per stage, with English conventional-commit messages
- At the end of each stage tell the user: what was done, how to test it by hand, known issues
- For uncertain design decisions, ask the user first; don't assume
- After each stage, update this file's "Development stages and progress"

# Session end procedure

> Note: items 1–3 and 6 exist only on the author's machine and don't appear in the public repo.

After each piece of work, in order:

1. Update `context/current-task.md`
2. Update `context/progress.md`
3. Update `context/todo.md`
4. If there was an architecture / design change or an important decision → add an entry to `context/decisions.md` (append only, never overwrite existing records) — **in both languages** (`decisions.md` and `decisions.zh-TW.md`)
5. If the project summary changed → update `context/project-summary.md` (keep it short, 1–3 pages, no work log) — **in both languages**
6. Add an entry to `context/session-log.md` (newest at the top, at most 10 lines each)

Any change to `CLAUDE.md`, `AGENTS.md`, `README` or `CHANGELOG` is made in both languages too (see the "Language policy" in `AGENTS.md`).

When done, output: **What was done**, **How to test by hand**, **Known issues**, **Suggested next steps**. Don't re-output all the Markdown contents.

# Context management principles

- Chat is short-term memory; Markdown is permanent memory. All long-term information must be written into this file or `context/*.md`; don't depend on chat history.
- A new session should be able to restore the full working state just by reading the Markdown files above.
- When background is needed, prefer citing the Markdown; avoid repeating the project background, architecture, tech stack or finished work in chat — Markdown always takes priority over chat history.
